# v1.0 — Google Gemini 3.x cross-vendor benchmark

> Fourth (and final) leg of the v1.0 cross-vendor sweep, covering
> Google's latest generation: Gemini 3.1 Flash-Lite (GA 2026-05-08, one
> week old at probe time) and Gemini 3.1 Pro Preview (GA 2026-02-19).
> **The generational gap from 2.5 → 3.1 is the most striking single
> finding of the entire v1.0 cross-vendor sweep.**

## Setup

- **Models**: gemini-3.1-flash-lite, gemini-3.1-pro-preview
- **Task**: identical graded K-hop bench (`runs/bench.jsonl`, 4 tiers)
- **Compute knob**: `thinking_budget_tokens` ∈ {1024, 4096, 16384}
  (adapter auto-detects "gemini-3" in model name and switches to
  `thinking_level` low/medium/high under the hood — the depth-lens-side
  API stays unchanged)
- **Samples per cell**: 16
- **Wall time**: ~10 min total (5× faster than 2.5 Pro)

## 🔥 Generational jump — the headline

Same task, same cheapest-tier price-class:

| Model | Generation | Tier 1 | Tier 2 | Tier 3 | Tier 4 |
|---|---|---:|---:|---:|---:|
| gemini-2.5-flash | 2.5 | 0.69 | 0.38 | 0.25 | **0.00** |
| **gemini-3.1-flash-lite** | **3.1** | **1.00** | **1.00** | **1.00** | **1.00** |

A model that **GA'd one week before this probe** completely closes the
capability gap that the previous generation's cheap tier could not solve.
The 2.5 → 3.1 jump on Gemini's cheap tier is bigger than the
Haiku-4.5 → Opus-4.7 jump on Anthropic at the same task class.

**For practitioners on the Gemini stack**: if you benchmarked Flash
before May 2026, your conclusion is now wrong. The cheap tier *just*
got viable.

## Cost / latency profile

3.1 Pro Preview was substantially faster than 2.5 Pro on the same
prompts (~7 min vs ~44 min wall-clock for the same 192 calls). Either
Google sized up the inference infra for 3.1, or the new `thinking_level`
control is producing tighter computation budgets than the old free-form
`thinking_budget`.

The 3.x adapter path used `thinking_level` mapped from the int budget:
- budget ≤ 2048 → `low`
- budget 2049-8192 → `medium`
- budget > 8192 → `high`

Both models took the same wall-clock for "low" and "medium" cells,
suggesting the model decides actual compute based on the prompt rather
than the level — same `enabled` ≠ `filled` behaviour we saw on Claude.

## What this means for depth-lens

This is the result that **justifies the entire framework**. None of the
other 3 vendor probes (Anthropic, OpenAI, Gemini 2.5 Pro) produced any
non-1.00 accuracy. Gemini 2.5 Flash was the lone differentiator — and
**that finding is now obsolete because Flash got replaced by Flash-Lite
3.1 in May 2026**. A practitioner relying on a one-shot 2025 benchmark
would now make wrong tooling decisions.

depth-lens-style sweeps run cheaply enough to redo when the model line
changes ($0.60 for the full 4-cell × 3-budget × 16-sample × 2-model
Gemini bench). This is exactly the use case the tool exists for.

## Reproducing

```bash
export GOOGLE_API_KEY=...  # billing-enabled project
depth-lens compare \
    --models gemini:gemini-3.1-flash-lite,gemini:gemini-3.1-pro-preview \
    --task custom:runs/bench.jsonl:first_int \
    --depths 1,2,3,4 --compute 1024,4096,16384 \
    --n-samples 16 \
    --plot gemini3.png --save-json gemini3.json
```
