# v2.1 — Customer-reply quality: an LLM-as-judge case study

> **The third leg of the real-estate-management chatbot.** v1.2 measured
> *urgency classification* (`exact` scorer) and v1.2/MSP measured
> *quote calculation* (`first_int` scorer). Both used structured-output
> scorers. This study completes the picture by measuring **free-form
> reply quality** with the v2.1 `llm:` scorer — the same workflow,
> applied to the kind of task where "did the model do a good job" needs
> human-like judgment.
>
> Total cost to produce: ~$1 + ~10 min.

## The task

A property-management chatbot composes a reply (free-form Japanese) to
an incoming tenant inquiry. The reply must satisfy **all three** of:

| Criterion | Why |
|---|---|
| (a) **Polite** — uses appropriate 敬語; no curt or dismissive phrasing | This is going to a paying tenant; tone failure has retention cost |
| (b) **Addresses the specific issue raised** — not generic boilerplate | Tenants ignore "we'll get back to you" replies. Specificity = trust |
| (c) **Proposes a concrete next step** — call this number, send this form, expect callback by X | A reply without an action item shifts the burden back to the tenant |

This goes through the v2.1 `llm:openai:gpt-5-mini:rubric:<rubric-text>`
scorer. The judge (gpt-5-mini at default effort) reads the inquiry,
the reference reply (target), the model's reply, and the rubric, then
outputs `Score: 0` or `Score: 1`.

## Bench

12 hand-crafted tenant inquiries across 4 categories:

- **緊急系 (3)**: water leak, lockout, gas-smell
- **事務手続き系 (3)**: move-out, late rent, renewal-doc missing
- **規約質問系 (2)**: pet permission, motorcycle parking
- **苦情系 (2)**: noise from upstairs, dispute next door
- **設備故障系 (2)**: aircon broken in heat, intercom not ringing

Each row has a reference reply written to exemplify the rubric.

## Models tested

| Model | Effort levels |
|---|---|
| `openai:gpt-5-mini` | low / medium / high |
| `openai:o4-mini` | low / medium / high |

(Judge: `openai:gpt-5-mini` at default-low effort — cheapest competent
judge in our pricing table.)

## Results

| Config | Accuracy | Pred latency (12 prompts) | Per-reply latency | Notes |
|---|---:|---:|---:|---|
| **`openai:gpt-5-mini @ effort=low`** ← winner | **12/12 (100%)** | 16.6 s | **1.4 s** | Cheapest + fastest config that meets the bar |
| `openai:o4-mini @ effort=high` | 12/12 (100%) | 21.6 s | 1.8 s | Same accuracy, ~30% slower per reply, also ~3× cost |
| `openai:o4-mini @ effort=low` | 11/12 (92%) | **7.7 s** | **0.6 s** | Fastest overall but 1 miss; acceptable if "92%" survives review |
| `openai:o4-mini @ effort=medium` | 10/12 (83%) | 12.9 s | 1.1 s | Strict loss vs both low and high |
| `openai:gpt-5-mini @ effort=medium` | 9/12 (75%) | 36.4 s | 3.0 s | Strict loss |
| `openai:gpt-5-mini @ effort=high` | 9/12 (75%) | **186.9 s** | **15.6 s** | Worst of all worlds — slowest, worse than `low`, ~12× per-reply latency |

## Three findings depth-lens surfaced

### Finding 1 — Higher effort is NOT monotonically better for free-form quality

For `gpt-5-mini`, accuracy **decreased** as effort went up
(low 100% → medium 75% → high 75%). The likely mechanism: at higher
effort, the model writes longer, more elaborate replies that **over-
think** the rubric and produce overly hedged or padded text that the
judge marks down for failing the "addresses the specific issue" or
"concrete next step" criteria.

For `o4-mini`, the pattern is the *opposite* — accuracy
**increased** with effort (low 92% → medium 83% → high 100%). Same
task, same rubric, opposite optimal effort.

The production lesson: **the right "effort" knob isn't model-agnostic
even on the same task**. You have to measure per (model × task) cell,
which is exactly what depth-lens does.

### Finding 2 — Per-reply latency at `gpt-5-mini @ high` is **15.6 seconds**, which would kill any chat-UI rollout

The accuracy table doesn't tell you that `gpt-5-mini @ high` is a
strict no-go — it's 75% accuracy + 12× the per-reply latency of
`@ low`. depth-lens's combined latency × accuracy × cost output is what
prevents a team from choosing this config because "high effort sounds
more careful."

### Finding 3 — `gpt-5-mini @ effort=low` is the right call for this task, despite v1.0-v1.2 case studies suggesting `gpt-5-mini @ low` won't always be enough

The v1.0 cost-savings finding showed `gpt-5-mini` saturates many
structured tasks at low effort. The v1.2 self-hosted case study showed
`gpt-5-mini` was the winner for both urgency classification and quote
calculation. **This case study confirms the same model is the right
call for free-form customer-reply quality too** — but the *reason* we
know now (rather than guessing) is the LLM-as-judge scorer measured it
explicitly against the 3-criterion rubric.

In other words: **v2.1's contribution is not the conclusion — it's the
ability to verify the conclusion for an open-ended task.** Without the
LLM judge, this case study could not have been written.

## Reproducing

```bash
# 1. Write the bench (12 inquiries with reference replies).
# See runs/cs3_tenant_replies.jsonl in the repo, or write your own.

# 2. Run the case-study script (Python — uses depth-lens scorers
# directly because the CLI doesn't yet expose a free-form system
# prompt; see ROADMAP v2.2).
python runs/cs3_tenant_reply_case_study.py

# 3. Inspect the per-cell accuracy table (printed) and per-prompt
# scores (saved to runs/cs3_tenant_replies_results.json).
```

The same workflow scales to other open-ended tasks (RAG citation
faithfulness, sales-reply tone, code-review comment quality) by
swapping the bench JSONL and the rubric string. **The judge call is
just another API call** — same Wilson 95% CIs, same cost projection,
same depth-lens machinery as the structured-scorer case studies.

## Caveats

- **Judge cost is real but not surfaced in `recommend`'s `$/k-pred`
  output yet** (v2.2 TODO). Each prediction triggered one judge call;
  with 12 prompts × 6 configs that's 72 judge calls at ~$0.002 each
  ≈ $0.15 total — small here, but watch this column on larger benches.
- **Judge agreement isn't measured.** Each prompt was judged once. For
  borderline rubric criteria a future improvement is to judge each
  prediction multiple times (multiple judge runs, multiple judge
  models) and report inter-judge agreement.
- **Single rubric.** Different teams will phrase the criteria
  differently. The point isn't this exact rubric — it's that depth-lens
  lets you *swap the rubric and re-measure in 10 min*.
